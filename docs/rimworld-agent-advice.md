# RimWorld modding advice for coding agents

> This guide is a work in progress.

Use this guide when writing or changing a RimWorld mod with a coding agent. The aim is to make the requested change while preserving other mods' behavior, translations, and saved games. For project setup and patch registration, follow [Write a RimWorld mod with Disharmony](obj/guides/rimworld.md).

## Check the code for the game version you are targeting

Decompile the installed game's `RimWorldWin64_Data/Managed/Assembly-CSharp.dll` with [ILSpy](https://github.com/icsharpcode/ILSpy). Read the target method and its callers before choosing a patch. Check the installed game's XML Defs when changing data.

Do not rely on decompiled RimWorld source found on GitHub unless you have verified that the relevant code matches the game version you are targeting. A familiar method name does not mean its signature or behavior is unchanged. Existing mods are useful examples, but check their version assumptions too.

[Krafs.Rimworld.Ref](https://github.com/krafs/RimRef) supplies signatures for compilation, not executable game code. It cannot tell you what a method does. If you cannot inspect the relevant implementation, ask the mod author for it rather than guessing. [Plan a patch for your game](planning-a-game-patch.md) explains the investigation process.

## Use RimWorld's existing ways to add or change behavior

Choose the approach based on what needs to change:

- **Change data the game already exposes in XML:** use [PatchOperations](https://rimworldwiki.com/wiki/Modding_Tutorials/PatchOperations) to change the relevant Def fields. This can change a recipe or a configured stat without a method patch. It cannot change an arbitrary calculation or directly target Defs generated by C# rather than XML. Patches to the same field can still conflict; check the target nodes and load-order effects.
- **Add behavior the game already implements:** reuse an existing comp and configure its properties in XML. This can save you from reimplementing features such as refueling. Check that the comp supports the kind of object you are adding it to and that its actual behavior fits the request; adding a comp does not make its behavior freely customizable.
- **Add behavior or state to individual objects:** consider a custom [component](https://rimworldwiki.com/wiki/Modding_Tutorials/Custom_Comp_Classes). A [ThingComp](https://rimworldwiki.com/wiki/Modding_Tutorials/ThingComp), for example, can add an action button or track state separately for each building through the game's callbacks. It requires a `ThingWithComps` host, and its hooks do not let you intercept every calculation. Check the relevant hooks in the target game's code. Save persistent fields explicitly.
- **Add configuration to a Def:** use a [DefModExtension](https://rimworldwiki.com/wiki/Modding_Tutorials/DefModExtension) for extra flags or parameters that your code reads. It works across Def types without replacing their classes. The extension does nothing by itself: a component, patch, or other code must use it. Its values belong to the Def and are shared by objects using that Def; do not store an individual building's remaining fuel or a pawn's current progress there.
- **Change an existing calculation or method's behavior:** use a Harmony or Disharmony patch to change the relevant code without adding a component to each object. A patch can adjust arguments, results, or an operation inside the method without replacing the object's class. It depends on the target code and can interact with other patches, so inspect callers, limit its scope, and recheck assumptions after game updates. The next section explains how to preserve the original behavior.

ThingComps add ticking overhead on every instance, even when the feature needs no ticking. This applies to both existing and custom ThingComps. When a targeted method patch and a ThingComp can both achieve the change, consider that cost rather than automatically choosing the comp.

These approaches can work together: XML can attach a component or configure a `DefModExtension`, and a method patch can read that configuration. See the community [guide to modifying Defs](https://rimworldwiki.com/wiki/Modding_Tutorials/Modifying_defs) for alternatives, including custom classes.

When changing an existing Def, avoid copying and replacing the entire definition for a small change. That can discard unrelated changes from other mods. Similarly, replacing an existing object's class can conflict with another mod that wants to use its own class. Check what you need to replace before choosing that approach.

## Preserve the original method when possible

Avoid a prefix that returns `false` and skips the original method when an alternative is available. Skipping it removes the game's behavior and can prevent other patches from taking effect as their authors intended. Harmony's [prefix documentation](https://harmony.pardeike.net/articles/patching-prefix.html) recommends postfixes or transpilers for small changes rather than replacing the method.

Choose the patch to match the change:

- To adjust an input, use a prefix that lets the original run.
- To adjust a calculated result or add behavior afterward, use a postfix. Modify the result you receive rather than recalculating it from scratch and discarding other mods' changes.
- To change one call inside a particular method, consider a Disharmony inner patch. [The worked comparison](harmony-comparison.md#worked-comparison-change-a-call-inside-a-method) shows how to leave other callers unchanged.

Skipping the original is sometimes the intended behavior. In that case, limit the skip to the circumstances that need it and account for the original method's side effects as well as its return value.

## Give your Defs and assets distinctive names

Prefix new `defName` values with a mod-specific identifier, such as `TrailTools_TravelPack`. Def names are shared across loaded mods within each Def type; your mod folder and C# namespace do not isolate them. Two mods defining the same name can collide. The [Def compatibility guide](https://rimworldwiki.com/wiki/Modding_Tutorials/Modifying_defs#Overwriting_Defs) explains the problem.

Use the same approach for XML inheritance `Name` attributes you introduce. These are identifiers too; see [abstracts and inheritance](https://spdskatr.github.io/RWModdingResources/abstracts.html). Keep existing identifiers when updating a published mod unless you have planned how to preserve references to them.

Put textures under a distinctive path such as `Textures/TrailTools/Items/TravelPack.png`. Reference that as `TrailTools/Items/TravelPack`, without the `Textures/` prefix or file extension. Reusing another mod's texture path can replace its art depending on load order. See the community [texture guide](https://rimworldwiki.com/wiki/Modding_Tutorials/Textures).

## Use RimWorld's built-in translation system

Do not build a separate language selector, translation dictionary, or file loader. Use RimWorld's translation system so translators can add a language without changing your C# code.

Put text used by C# UI code in a file such as `Languages/English/Keyed/TrailTools.xml`, even if you only provide English initially:

```xml
<LanguageData>
  <TrailTools_ShowRange>Show range</TrailTools_ShowRange>
</LanguageData>
```

With `using Verse;`, obtain the text inside your UI method with:

```csharp
string label = "TrailTools_ShowRange".Translate();
```

Prefix translation keys just like Def names. For sentences containing values, put the whole sentence in the language file and pass the values to `Translate`; do not concatenate translated fragments in English word order.

For Def labels and descriptions, use the normal translatable Def fields and `Languages/<language>/DefInjected/<DefType>/` translations. Do not translate `defName` identifiers or use translated labels to identify a Def in code. The [localization guide](https://rimworldwiki.com/wiki/Modding_Tutorials/Localization) explains `Keyed`, `DefInjected`, and translation arguments.

## Save state through RimWorld's saving system

If a feature adds state that must survive reloading a colony, implement the saving hook provided by the class that owns that state: `ExposeData`, `CompExposeData`, or `PostExposeData`. Preserve the base class's saving behavior when overriding it.

For each field, identify its type and whether it contains an object saved here or refers to one saved elsewhere. That determines the correct `Scribe` method. Common cases are:

| What the field holds | How to save it |
| --- | --- |
| Supported simple values, such as numbers, booleans, enums, or strings | `Scribe_Values` |
| A reference to a Def | `Scribe_Defs` |
| An `ILoadReferenceable` object saved elsewhere, such as a spawned pawn | `Scribe_References` |
| A custom `IExposable` object whose contents must be saved here | `Scribe_Deep` |
| A collection | `Scribe_Collections`, with the correct `LookMode` for its contents; dictionaries need the correct mode for both keys and values |

Deep-saving an object that is already saved elsewhere can recreate it instead of restoring a reference to the existing object. Reference-saving an object that is never saved elsewhere cannot restore its contents. Determine how the object is saved before writing the call. The community [saving guide](https://spdskatr.github.io/RWModdingResources/saving-guide.html) explains the methods and their requirements.

A static dictionary is not saved automatically. Keep caches tied to their game or map and clear or rebuild them when that context changes. Check that loading a different colony does not reuse state from the previous one.

## Size textures for how they appear in-game

For small item, weapon, or apparel textures, start with 128×128 or 256×256 rather than shipping a large generated image. Prefer power-of-two dimensions such as 128×128 or 256×128. Larger textures use more video memory without necessarily adding visible detail.

This is a sizing guideline, not a universal 256×256 limit. Large buildings and texture atlases may need larger images. Choose dimensions based on the object's draw size and any required atlas layout, and inspect the result in-game. The [texture guide](https://rimworldwiki.com/wiki/Modding_Tutorials/Textures) covers pixels per tile, texture paths, and linked atlases.

## Verify the mod in-game before calling it finished

A successful build does not establish that the game loaded your mod or that its patches work. Use the [RimWorld tutorial's verification steps](obj/guides/rimworld.md#verify-in-game), then check the situations relevant to your feature:

- Run with only the required dependencies first.
- Try the intended behavior and nearby cases that should remain unchanged.
- Save, quit, and reload if the feature adds persistent state. Also check an existing save when the mod is intended to support it.
- Test with relevant mods that change the same behavior. A clean test with your mod alone does not establish compatibility.
- If DLC or another mod is optional, test with it disabled as well as enabled. Declare required dependencies in `About.xml` instead of assuming they are present.

Report which checks actually ran and what remains unverified. If you cannot run RimWorld, give the mod author the in-game checks still needed; do not present compilation as an in-game test.

## Investigate log warnings and errors; do not hide them

After every in-game test session, check the full `Player.log` for warnings and errors, even if the feature appeared to work. Read the log before launching the game again so you are checking the session you just tested. On Windows, the usual location is `%USERPROFILE%\AppData\LocalLow\Ludeon Studios\RimWorld by Ludeon Studios\Player.log`; see the [log-file locations](https://rimworldaccess.com/reference/reporting-bugs/#attach-your-log-file) for Windows and macOS.

For each warning or error, read the message and any stack trace, identify what caused it, and fix the root cause. Start with the earliest relevant failure: later errors may be consequences of it. Rebuild, repeat the test, and check the new log to confirm the fix.

**Do not suppress warnings or errors by patching the game's error-reporting functionality**, such as `Verse.Log.Warning` or `Verse.Log.Error`. Hiding a message leaves the fault in place and prevents players and other mod authors from diagnosing it. Mod authors have been banned from the Steam Workshop for doing this.

If a message may come from another mod or the game itself, reproduce it with only the required dependencies and compare with a run without your mod where possible. If you cannot determine or fix its cause, report the message, reproduction steps, and what you checked to the mod author. Do not hide it or describe the test as error-free.
